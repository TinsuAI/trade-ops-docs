# Architecture Decisions

## [2026-04-24] Separate Proposal Workspace From Case Analysis
**Context:** The Growatt case repository contains deep case-specific analysis, local data artifacts, and execution outputs. A broader product proposal for a multi-client operational platform would become noisy and hard to maintain if it stayed in that repo.
**Decision:** Create a separate docs-first project at `/home/vp/workspace/client/tradeops`.
**Alternatives:** Keep proposal notes inside the Growatt case repo; create only a subfolder inside the existing repo.
**Consequences:** Proposal framing stays clean, client-facing documents can evolve independently, and raw case artifacts remain isolated.

## [2026-04-24] Position The Product Below ERP, Above Simple Document Storage
**Context:** The emerging scope covers BOM, CO dossiers, customs declarations, and settlement reporting, but does not yet include the full finance, procurement, warehouse execution, or production-control surface of ERP.
**Decision:** Frame the product as a trade-compliance operations platform, not a full ERP.
**Alternatives:** Pitch it as a BOM builder; pitch it immediately as ERP.
**Consequences:** The proposal can stay credible, focused, and expandable without overpromising on enterprise breadth too early.

## [2026-04-24] Start As A Docs-First Proposal Project
**Context:** The immediate need is to shape the narrative, scope, and rollout logic. There is no confirmed app stack yet.
**Decision:** Use a Markdown-first repository with proposal and discovery documents before choosing a software stack.
**Alternatives:** Scaffold a web app immediately; start directly with a slide deck only.
**Consequences:** The project can move quickly on framing while keeping technical options open.

## [2026-04-26] Tenant Model: Per-Broker Deployment, Multi-End-Client Within
**Context:** TradeOps is sold by Tinsu AI to customs brokers. Each broker (the first one being Trọng Tín - Hoa Nam) serves many end-clients — DN chế xuất and SXXK enterprises whose data flows through the broker. Brokers compete with each other and have no reason to share infrastructure or data. Selling TradeOps to additional brokers in the future means a separate engagement and a separate deployment, not a shared multi-tenant SaaS.
**Decision:** Each broker gets a fully independent TradeOps deployment. The application's tenant model is single-level: multi-end-client within one broker's instance. Brokers are kept separate at the infrastructure layer, not at the application layer. There is no "broker" entity in the data model.
**Alternatives:** Shared multi-tenant SaaS hosting many brokers (more cost-efficient operationally, but creates avoidable confidentiality concerns; brokers cannot be told their competitors are on the same instance); single-tenant per end-client (impossibly expensive to operate, would make broker portfolio management impossible).
**Consequences:** The application is simpler — only end-client tenancy needs row-level access control inside the database. "Multi-broker capability" lives at the deployment / packaging layer (Tinsu AI internal concern), not in client-facing proposal language. Each new broker engagement is a deployment task, not a configuration change. Per-broker customization stays cheap because there is no shared codebase concern across brokers.

## [2026-04-26] Center Of Gravity: Document-First With Selective Structured Overlays
**Context:** The pain points are anchored in document chaos — version drift, scattered channels, broken traceability. A master-data-first design (BOM tables, material masters, declaration tables) would deliver structure but takes longer to ship and risks rebuilding ERP-style modules that the broker's end-clients may already have. A pure document repository would ship fast but would not solve BOM versioning, CO traceability, or settlement reconciliation.
**Decision:** The system is document-first: every artifact (BOM file, invoice, packing list, declaration, CO dossier piece, settlement workbook) lives as a versioned, classified, related document. Structured data models are added selectively only where operations require them — item master, BOM headers and lines, declarations, dossier status, multiple inventory views — and these structured overlays are linked back to their source documents rather than replacing them.
**Alternatives:** Pure document store with metadata only (insufficient for BOM/CO operations); master-data-first ERP-shaped system (too heavy, too slow, overlaps with end-clients' existing systems).
**Consequences:** Ingestion, versioning, and search ship early and visibly. Item master, BOM, inventory views, and dossier modules layer on top without forcing data migration from existing systems. The risk is that the structured overlay can drift from the underlying documents, so a reconciliation/audit view becomes a first-class Phase-2 feature rather than an afterthought.

## [2026-04-26] System Role: Broker's Portfolio + Operations Platform, Categorically Distinct From The Three Workflow Apps
**Context:** Three concrete trade-compliance apps are currently being built for the same broker: Siafu (TKXK / TKNK declarations), Barry-CO (CO dossier preparation), Barry-BCQT (annual customs settlement reporting). All three codebases belong to Tinsu AI; within the team, the user owns Barry-CO and Barry-BCQT and the user's partner on the team owns Siafu. Each app handles its domain workflow. Two earlier draft framings of this proposal failed:  (a) positioning TradeOps as a "shared backbone" or "infrastructure layer" the three apps depend on — invites the customer objection "If your three apps need this to work, why didn't you build it into the three apps?";  (b) positioning TradeOps as a "daily operations platform" without naming a specific category of work that lives only in TradeOps — softer than (a) but still vulnerable to "why am I being sold 4 products?" because it does not point to work the three apps structurally cannot do. The work that genuinely exists only in TradeOps is portfolio management of N end-clients across years and audit defense over post-clearance years — both continuous, not trigger-driven, and outside the workflow apps' design scope.
**Decision:** TradeOps is the **broker's portfolio and operations platform** — the system the broker uses every day to manage the entire portfolio of end-clients across years (who the clients are, what dossiers exist, who is working on what, what the history is, what is defensible under audit). TradeOps' modules organize into two groups: **daily-ops modules** (Dossier & client management, Document control, Audit trail) as the headline of the platform, and **per-end-client master-data modules** (Item master + code translation, BOM master + period-flow data, Multi-view inventory) holding master data the daily-ops modules and the integrated workflow apps both read. TradeOps is **independent** of Siafu, Barry-CO, and Barry-BCQT, which are specialized workflow accelerators that fire on specific business triggers. The three apps integrate with TradeOps via published API contracts to read shared master data and to write their outputs back into the portfolio's dossier history; that integration is additive benefit, not the reason TradeOps exists. TradeOps does NOT own finance, procurement execution, or warehouse stock movement; ERP / accounting integration is a Phase-3 concern via bounded connectors.
**Alternatives:** Pitch as ERP replacement (overpromises, slow to win, hard to deliver, conflicts with end-clients' existing systems); pitch as a standalone fourth workflow app (duplicates Siafu / Barry-CO / Barry-BCQT functionality, no shared-data benefit); pitch as "shared backbone for the three apps" (the first prior draft framing — invites the customer objection "why didn't your three apps include this?", and misses that TradeOps is a different category of system, not infrastructure for the three); pitch as "daily operations platform" without portfolio + audit-defense framing (the second prior draft — softer than backbone but still vulnerable to "why 4 products?" objection because it does not name categorically distinct work). Sell as one bundled "Trade Compliance Suite" SKU with TradeOps as inner module set (cleanest customer narrative but sacrifices Tinsu AI's ability to sell TradeOps separately to other brokers later — rejected because Tinsu AI's commercial roadmap depends on that flexibility).
**Consequences:** The system diagram becomes: TradeOps (portfolio + ops platform) and the three workflow apps sitting alongside in the same broker deployment, integrating via published API contracts. Proposal narrative leads with the portfolio + audit-defense problem — managing N end-clients across years, defending dossiers under post-clearance audit, retaining staff knowledge across turnover — not with data inconsistency between the three apps and not with generic daily-ops chaos. Module structure organized into two groups (daily-ops modules + per-end-client master-data modules) without upper/lower hierarchy vocabulary. Phase 1 goal refocuses to "pilot end-client portfolio with daily-ops modules + master-data modules + one CO end-to-end as integration demonstration"; Barry-CO integration is positioned as the demonstration on top of an already-valuable portfolio, not as the goal. Internal codebase boundaries within the Tinsu AI team must be respected — TradeOps exposes data over **published API contracts**, not shared-database direct access; Siafu (owned by the user's partner) integrates through those contracts rather than being absorbed. Long-term, integration scope stays bounded and negotiable per engagement.

## [2026-04-26] Inventory Is Multi-View And Reconciled, Not Converged
**Context:** Customs brokers and their end-clients work with at least four legitimately divergent inventory views over the same NVL: physical warehouse stock, accounting NXT, balance derived from BCCT extracts (the line-level declaration data pulled from the HQ system; customs does not itself hold a "balance"), and CO inventory (consumption mapping per export shipment). The CO inventory in particular is a working ledger that maps NVL consumption to specific export shipments under origin rules — origin rules constrain which import lots can notionally feed which export shipments, so CO inventory legitimately diverges from physical warehouse stock without that being an error. Forcing convergence would break CO operations because the "right" NVL with the "right" provenance would not always be on paper at the right time. The inability to keep these views plausible while staying close enough to reality for BCQT reconciliation is one of the most expensive unsolved operational pains today.
**Decision:** TradeOps holds all relevant inventory views as first-class data, each linked back to its source documents and to the same underlying item master. The platform's job is to **reconcile and surface divergence between views**, with full audit trail, not to enforce a single converged truth. Divergence is data, not error.
**Alternatives:** Single-source-of-truth inventory (looks tidy on a slide, breaks the actual workflow); ignore inventory entirely and let each app keep its own (already today's broken state — exactly the pain TradeOps must address).
**Consequences:** Phase-2 reconciliation views become a first-class deliverable, not an afterthought. The proposal can credibly claim a differentiator that generic ERP, document storage, and BI tools were not designed for. Module 4 (multi-view inventory) is one of the harder pieces to design but also one of the highest-leverage to demo.

## [2026-04-26] Item Master + Code Translation As A Foundational Module Of The Platform
**Context:** Each end-client has its own catalog of finished products (SP), raw materials (NVL), and semi-finished products (BTP). Each item carries an internal ERP code AND one or more customs declaration codes (mã HQ). The relationship is many-to-many in practice: the same physical NVL has been declared under different mã HQ across years because of inconsistent classification and naming on TKNK forms. Without a stable item master that owns this many-to-many mapping, BOM versioning has no anchor, multi-view inventory cannot reconcile across ERP and HQ codes, and BCQT cannot match accounting NXT to DS NVL HQ.
**Decision:** Item master and the HQ↔ERP code translation table are a single foundational module of TradeOps in the per-end-client master-data modules group (Module 4). BOM, multi-view inventory, dossiers, and documents all reference items via the stable internal IDs this module owns. It is **not** an input table maintained inside one app (e.g. inside Barry-BCQT). All three workflow accelerators (Siafu / Barry-CO / Barry-BCQT) read from the same item master via stable internal IDs through the published API.
**Alternatives:** Keep code-translation lookup inside Barry-BCQT (duplicates effort across apps, drifts over time); fold item master into the BOM module (entangles two concerns and makes BOM versioning brittle); adopt HQ codes as the primary identifier (breaks the moment a code changes across declarations).
**Consequences:** Onboarding any new end-client begins with a non-trivial catalog setup task — extracted from historical TKNK + factory BOM + accounting export — that is itself a real deliverable, not invisible plumbing. This is also the bedrock of Tinsu AI's "data standardization advisory" service component for end-clients. Inter-app integration uses item master IDs as the canonical reference, never raw HQ codes or raw ERP codes alone.

## [2026-04-28] All 4 Apps Standalone, Sync Via API Contracts When Co-Deployed
**Context:** While walking through a Barry-CO + TradeOps integrated workflow scenario, the architecture's implicit assumption surfaced: Barry-CO would query BOM / item-master / inventory from TradeOps every step, which makes Barry-CO unable to function without TradeOps. This is a Path-1 ("bundle is the product") architecture in disguise and conflicts with the goal of selling each app independently. The earlier 2026-04-26 decision did say each integration is "via published API contracts, not shared-database direct access," but did not explicitly require each app to carry its own complete data model. Without that requirement, the workflow apps end up architecturally dependent on TradeOps even if they technically use API rather than shared DB.

**Decision:** Each of the 4 Tinsu AI apps (TradeOps, Barry-CO, Barry-BCQT, Siafu) is fully standalone-capable with its own complete data model. Each carries its own item master, BOM, inventory ledger, file storage, and workflow state for the entities it operates on. Standalone scope is narrower than integrated (Barry-CO standalone has no cross-customer view; TradeOps standalone has no auto C/O workflow engine), but each is fully usable on its own. When co-deployed for the same broker, sync happens via API contracts with **primary/mirror designation per entity type**: TradeOps is primary for master data (item master, BOM, inventory baseline, hồ sơ thương nhân); each workflow app is primary for its own workflow state, snapshots, and outputs (Barry-CO for C/O workflow; Barry-BCQT for BCQT; Siafu for declarations). Documents are primary in whichever app generated them; TradeOps mirrors all for portfolio + audit-defense view. Conflict resolution: primary wins; when a mirror tries to write to a primary-owned entity, the mirror UI is read-only.

**Alternatives:**
- (Path 1, status quo of memory pre-2026-04-28) Bundle architecture — TradeOps owns master, workflow apps query via API but cannot stand alone. Cleaner integration, no duplication, but each workflow app can only be sold to brokers who also buy TradeOps.
- (Path 3) Master Data Service as separate component — cleanest architecture (no duplication, all 4 apps consume MDS), but adds a 5th component to design + position + sell. Defers commercial complexity for cleaner code.
- (Mixed) Each app standalone, no sync at all — broker manually keeps duplicates aligned. Rejected because it negates the value of co-deploying.

**Consequences:**
- Each app becomes commercially independent. Barry-CO can sell to brokers who don't want TradeOps; Barry-BCQT can sell to brokers who only do BCQT; etc.
- Architecture diagrams change: each app has its own data store box; sync arrows are optional dotted lines, not load-bearing connections.
- Workflow demos must show **mode standalone** vs **mode integrated** as separate scenarios. Workshop demos for TT-HN should be explicit about which mode is being shown.
- TradeOps' value when co-deployed = **integration hub + portfolio overlay + cross-app audit defense**, not "the master layer everything queries". Multi-view inventory module gets a cleaner purpose: reconcile divergent inventory views from each app + outside (kho vật lý / NXT kế toán).
- TradeOps' value standalone = portfolio + master + audit defense + document control without specialised workflow speed.
- Memory files that asserted hard ownership ("must sit in TradeOps") softened to "primary in TradeOps when co-deployed; each app has its own when standalone." See `project_item_master_foundation.md` and `project_three_adjacent_systems.md` updates.
- Standalone-to-integrated migration is a real product event: when broker who has Barry-CO standalone subsequently adopts TradeOps, a 1-time bulk migration imports Barry-CO's master into TradeOps; thereafter TradeOps becomes primary, Barry-CO drops master to mirror mode.
- Sync mechanics that need design (not in this decision but called out): real-time webhook for events, periodic reconciliation as backup, on-demand pull on user refresh, schema versioning between apps that may deploy at different versions.
- Mockup `screens/document-control.html` and `screens/co-dossier.html` currently show **integrated mode** demo; they need a small "Mode integrated — broker có cả Barry-CO" annotation, plus eventually a parallel demo of standalone TradeOps mode if requested for Phase 1 pilots without Barry-CO.
